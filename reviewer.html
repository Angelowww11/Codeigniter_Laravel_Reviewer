1.1 The browser, server, and framework

PDF pages 1–9 · Course introduction, objectives, and request–response ↗

Key terms — identify the job

  • Request — The incoming HTTP message. Check its method and path.
  • Response — The server’s outgoing message, often rendered HTML.
  • Route — The rule connecting a request method and path to a handler.
  • Controller — The coordinator that receives the request and chooses the work and response.
  • Model — The data-access part and its related data rules.
  • View — The template that presents supplied data.
  • Capture — A value matched from a route pattern, then passed to the handler.
  • Document root — The directory the web server exposes. Use the intended public/ boundary.

A web application lets a user work through a browser while application code runs on a server.

  • In this course, PHP is the server-side language. The browser sends an HTTP request, such as GET /about.
  • The server runs the matching code and sends a response, often HTML.
  • The browser displays that response; it does not execute the server’s PHP source.

The word request means the incoming message asking the application to do something.

  • The response is what the server sends back. A URL identifies the destination, while the HTTP method helps express the action.
  • Merely typing a URL into the address bar normally makes a GET request.

A framework supplies structure and reusable tools for tasks that repeat across web applications: routing, database access, validation, security features, and organizing files.

  • Without shared structure, a developer can end up repeating setup and mixing SQL, validation, and HTML in every page.
  • Framework conventions give those responsibilities predictable locations.
Take note

The framework supplies tools; the developer still writes the application’s rules. Built-in security tools help only when the application uses and configures them correctly.

1.2 MVC: know who owns each job

PDF pages 10–18 · Responsibilities and request flow ↗

MVC stands for Model–View–Controller. It separates responsibilities so that a change to the interface does not require rewriting the data-access layer. These are cooperating parts of an application, not three unrelated definitions to memorize.

Part Main responsibility CodeIgniter location Task-manager example
Model Data access and related data/business rules app/Models Retrieve pending tasks
View Presentation of supplied data app/Views Print a task list as HTML
Controller Coordinate the request and response app/Controllers Ask for tasks, then choose a view

For a task-list request, the route selects a controller method.

  • The controller calls a model, receives the records, and passes them to a view.
  • The rendered HTML becomes the response. In the course’s MVC arrangement, the model does not build the page layout and the view does not query the database.

Example: changing the color and layout of a task list is a view change. Filtering the query to return only pending tasks is data-access work. Choosing which records and template to use for a request is controller coordination.

Separation supports maintenance, teamwork, testing, and reuse. The same data layer can support multiple presentations. This does not mean every feature requires a database call: an About page can use a route, controller, and view without needing a model.

Memory cue: Model = data; View = display; Controller = coordinator.

  • CodeIgniter 4 is the PHP MVC framework used in the first four modules.
  • The course introduces it as lightweight and beginner-friendly; the responsibility split matters more than promotional descriptions of a framework.

1.3 Installation, folders, and local configuration

PDF pages 19–32 · Setup and environment settings ↗

The module lists PHP 8.1 or newer, Composer, an editor, and a local PHP/MySQL setup such as XAMPP.

  • Treat the stated PHP version as the PDF’s classroom requirement; an actual framework release may require a different minimum.
  • Composer manages PHP packages. Install it on the machine, then check it with composer --version.
composer create-project codeigniter4/appstarter myproject
cd myproject
php spark serve

create-project downloads the starter into myproject.

  • Run the remaining commands inside that project directory. Spark is CodeIgniter’s command-line tool.
  • php spark serve starts its development server, usually at http://localhost:8080. The PHP executable still has to exist; this command simply avoids needing a separate Apache server for that local workflow.

The slides also show downloading the framework ZIP and running Apache through XAMPP.

  • These are alternative setup paths, not commands to run simultaneously. Under the illustrated XAMPP arrangement, a classroom URL may include /your-folder/public.
  • Keep the public-directory distinction clear when comparing it with Spark’s URL.
Folder or file What belongs there
app/Controllers Request-handling controller classes
app/Models Data-access model classes
app/Views HTML/PHP templates
app/Config Application settings, including Routes.php
public/ Web entry point and publicly served assets
writable/ Logs, cache, and other generated writable data
vendor/ Composer-managed packages in a Composer installation
.env Environment-specific local settings

The manual download and Composer layouts can differ. The slide’s reference to system/ versus vendor/ describes those distribution layouts; it does not change where your controllers, models, and views belong.

Public means publicly reachable

The web server should point at public/. Application source, dependencies, credentials, and writable internal data should not become downloadable just because the project folder is on the server.

The provided env template is renamed/copied to .env for local configuration. The following completes the missing closing quote visible in the PDF’s example:

CI_ENVIRONMENT = development
app.baseURL = 'http://localhost:8080/'

CI_ENVIRONMENT selects environment behavior.

  • app.baseURL is the application’s base address; keep its trailing slash. Match it to the server you actually use.
  • app/Config/App.php provides application configuration too; .env can supply the local value. The PDF also sets $indexPage = '' to omit index.php from generated URLs.
  • That setting alone does not configure Apache rewriting.

1.4 URLs, explicit routes, and captured values

PDF pages 33–38 · URL terminology and route patterns ↗

For https://www.example.com/blog/news/2022/10?page=2, separate the base address, path, and query string. The route path is considered relative to the application’s base. page=2 is query data, not another slash-separated path segment.

An explicit CodeIgniter route combines HTTP method + path pattern + handler. Routes belong in app/Config/Routes.php.

$routes->get('/about', 'Pages::about');
$routes->get('/profile/(:num)', 'Pages::profile/$1');

The first route answers GET /about by running about() in Pages.

  • In the second, the numeric URL component is captured and passed as the first argument.
  • Visiting /profile/123 supplies 123 to profile($id). $1 means the first captured placeholder, not a fixed literal user ID.
Placeholder What to recognize
(:num) Numeric route component, used for an ID in these examples
(:segment) One component; cannot include /
(:any) The remaining path; may span multiple components
(:alpha) Alphabetic characters
(:alphanum) Alphabetic and numeric characters
(:hash) Same matching behavior as (:segment), but communicates intent

Do not mix two routing explanations. The PDF’s /blog/post/20261231 segment illustration helps label controller/action/argument-style URLs.

  • With an explicit route, however, the handler is whatever the route declares; a URL does not have to use the controller’s class name.
  • A captured ID is also not proof that the record exists or that the visitor may access it.

1.5 Controllers, index(), and clean URLs

PDF pages 39–44 · Class structure and URL handling ↗

<?php
namespace App\Controllers;

class Pages extends BaseController
{
    public function about()
    {
        return 'This is the about page.';
    }
}

Save this class as app/Controllers/Pages.php.

  • The namespace places it in the application’s controller namespace. extends BaseController inherits the project’s base controller behavior.
  • A public method is an action that an appropriate route can target.
  • Returning text creates a simple response; later, returning a view creates an HTML page.
Clarification: index is not an automatic first step

M1 p. 42 calls index() the first function to execute. More precisely, it is a conventional/default action when routing selects it. An explicit Pages::about route calls about() directly; it does not run index() first. See the official default-method explanation.

To map the root URL explicitly, use $routes->get('/', 'Pages::index');. The method name alone does not register that URL.

The clean-URL slides discuss removing public/index.php/ from a classroom URL.

  • Their alternatives include moving index.php/.htaccess, which the PDF discourages for hosted applications, and a root rewrite into public/.
  • The underlying distinction is between the server’s document root, rewrite behavior, and generated URL settings.
  • Prefer the intended public/ document root; do not treat relocating files as a universally safe deployment recipe.
  • The supplied Apache .htaccess examples depend on Apache and rewrite support.

1.6 Views and controller-to-view data

PDF pages 45–54 · Rendering, data, organization, and recap ↗

Create app/Views/about.php, then render it with return view('about');. The view name omits .php. view() renders a template; it is not a redirect to another URL.

// In Pages::about()
$data = ['title' => 'Sample Page', 'name' => 'Pages'];
return view('about', $data);

<!-- app/Views/about.php -->
<h1><?= esc($title) ?></h1>
<p>About <?= esc($name) ?></p>

The array key name becomes $name in the view.

  • The controller could obtain that value from an array, a database, or another service; the view only needs the supplied value.
  • The esc() calls are an explicit safe-output addition to the PDF’s very short dynamic-data example.

Subdirectories: view('directory-name/about') looks under app/Views/directory-name/about.php.

Several templates in one response: the course concatenates rendered views using the PHP dot operator:

return view('header', $data)
    . view('menu')
    . view('main', $data)
    . view('footer');

This produces one response made from several rendered pieces. Pass data to the templates that need it. The order controls the resulting page order.

Before leaving M1: be able to trace route → controller → view → browser, identify each project folder, and explain why a view receives data rather than fetching it.

  • A missing namespace, wrong view name, unmatched HTTP method, or stale browser output can make correct-looking code appear broken.
  • The final pages recap these mistakes and provide a Q&A prompt; they add no separate API.

1.7 Additional setup and URL details

PDF pages 20–44 · Installation alternatives and configuration examples ↗

Check the installation tools separately. Composer installs PHP packages.

  • XAMPP supplies a local server stack. Spark starts the CodeIgniter development server.
  • VS Code edits the application files. The Composer version displayed in the slide is example output, not a required version for every project.

The slide gives two local addresses: http://localhost:8080 for Spark and http://localhost/your-folder-name/public for the illustrated XAMPP arrangement. Start Apache in XAMPP when you use the Apache arrangement. Start MySQL when the application needs the database.

The application can also obtain its base address from app/Config/App.php. The slide shows these configuration properties:

public $baseURL = 'http://localhost/your-folder-name/';
public $indexPage = '';

These are the PDF's property examples. Preserve the property types required by the generated configuration class in your installed version. The base URL, document root, and rewrite rules are separate settings.

Read the URL relative to the application. For https://www.example.com/blog/news/2022/10?page=2, a base URL of https://www.example.com/blog/ leaves news/2022/10 as the application-relative path. The query remains page=2. A subfolder in the base URL changes the relative route path.

The URL-cleaning slide includes this root-directory .htaccess example:

<IfModule mod_rewrite.c>
    RewriteEngine On
    RewriteRule ^(.*)$ public/$1 [L]
</IfModule>

This is the PDF's Apache-specific alternative.

  • RewriteEngine On enables rewriting. The rule forwards the captured path into public/. [L] stops processing further rules in that pass.
  • The application's public/.htaccess handles its own front-controller rewriting. These files require an Apache configuration that permits the relevant overrides.

The other printed alternative moves index.php and .htaccess from public/ into the project root.

  • It changes the path reference from ../app/Config/Paths.php to app/Config/Paths.php. The PDF does not recommend this alternative for hosted applications.
  • Keep the normal public/ document root when you control the server configuration.

Check the complete route match. A route requires the correct HTTP method and path. A public controller method does not register its own explicit route. (:any) can capture multiple path components, while (:segment) captures one. (:hash) communicates the intended identifier type but does not hash, decode, or validate an identifier's ownership.

Apply the concepts: trace the request

These worked situations apply the module’s ideas to new values. They add reasoning practice without changing the framework conventions.

Situation 1 — The form submits, but the action never runs.

  1. Identify the actual request: for example, POST /contact.
  2. Compare its method and path with the route definition.
  3. A get('/contact', ...) rule does not receive that POST request.
  4. Register the intended submission route and connect its handler.

Result: diagnose dispatch before changing the view or data layer. A correct controller cannot process a request that does not reach it.

Situation 2 — The controller has data, but the template reports an undefined variable.

  1. Read the data key passed to view(): ['displayName' => $name].
  2. That key creates $displayName in the view.
  3. Make the template variable and data key agree.

Result: the controller’s local variable name does not automatically become the view’s variable name.

Situation 3 — Clean links fail only under Apache.

  • Known fact: an empty indexPage setting removes index.php from generated links.
  • Separate requirement: the web server must rewrite incoming clean paths through the public entry point.
  • Next check: inspect the document root and rewriting setup before moving internal files into public access.

Exam cue: name the failed connection: request → route → controller → data → view → response. Correct the step supported by the evidence.

2.1 What the database adds

PDF pages 1–9 · Objectives, persistent records, schema, and sample data ↗

Key terms — identify the job

  • Schema — The tables, columns, types, and constraints in the database.
  • Primary key — The unique row identifier; it is not the row’s position in a list.
  • Model configuration — The table, key, return type, and writable fields used by a model.
  • Filter — A condition selecting matching rows, such as status=pending. This is a query filter, distinct from an authentication filter.
  • Order — The sequence of results. DESC places greater or later values first.
  • Limit — The maximum number of returned rows.
  • Retrieval — The operation that executes the prepared selection and returns records.
  • Escaping — Output handling for the display context; it does not replace query construction or validation.

A database holds records that survive application restarts and can be read or changed across requests. A hard-coded array is useful for demonstrating a view, but it does not become a persistent shared task list merely because it looks like one in the browser.

The course uses a tasks table throughout the examples:

CREATE TABLE tasks (
    id INT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(150) NOT NULL,
    status VARCHAR(20) DEFAULT 'pending',
    created_at DATETIME
);

INSERT INTO tasks (title, status, created_at) VALUES
('Buy groceries', 'pending', NOW()),
('Submit report', 'pending', NOW()),
('Fix login bug', 'done', NOW());

id uniquely identifies a row and is generated automatically.

  • title allows up to 150 characters and cannot be SQL NULL. status defaults to pending if omitted.
  • created_at stores a date and time; this schema does not itself give that column an automatic default.
  • The sample INSERT explicitly supplies NOW().
Two separate setup steps

Creating a table does not insert its sample records. An empty task list can mean the connection and query worked correctly but the table has no rows.

2.2 Database configuration and useful error clues

PDF pages 10–16 · Environment settings and troubleshooting ↗

The local .env connection identifies the server, database, account, password, and driver:

database.default.hostname = localhost
database.default.database = your_database_name
database.default.username = root
database.default.password =
database.default.DBDriver = MySQLi

The blank password and root account belong to the illustrated local setup; substitute the actual local account values rather than assuming every database uses them.

  • app/Config/Database.php defines database configuration defaults. Matching .env values override those defaults, so avoid keeping conflicting credentials in multiple places.
  • Local secrets should not be committed to a repository.
Symptom in the course What to check first
Unknown database The configured database name actually exists
Access denied Username, password, and the account’s access
Connection refused MySQL is running and the configured host/port is reachable
Edited settings seem ignored Correct .env file, key spelling, and active configuration
Clarification: test with an actual database operation

M2 p. 14 says to visit any page to test the connection. A static page may never access the database. Load a database-backed route or make a query before concluding the connection works. Reaching the CodeIgniter welcome page proves the application starts, not that every database credential is valid.

2.3 A model gives a table a PHP interface

PDF pages 17–20 · TaskModel and model properties ↗

<?php
namespace App\Models;

use CodeIgniter\Model;

class TaskModel extends Model
{
    protected $table = 'tasks';
    protected $primaryKey = 'id';
    protected $allowedFields = ['title', 'status'];
}

Save this as app/Models/TaskModel.php. The class extends CodeIgniter’s Model, which provides common record methods. $table selects the database table. $primaryKey identifies the column used by primary-key operations such as find($id). $allowedFields lists fields accepted by protected mass-assignment-style writes through the model.

An allowed field is not automatically a valid field. Allowing title means that field may be written through the model; validation still has to decide whether the submitted title is acceptable. Adding a field here also does not create a database column. Schema, validation, and writable-field configuration are separate responsibilities.

The course uses one model per table as its starting convention. That helps beginners map a class to a table; do not interpret it as a requirement that every possible application must have exactly one class for every table.

2.4 Read queries: selection, filtering, order, and execution

PDF pages 21–27 · Query Builder and model retrieval ↗

Query Builder lets PHP method calls describe a query.

  • Normal value arguments are escaped/bound by the framework rather than being pasted into hand-built SQL.
  • This reduces routine SQL mistakes; it does not make arbitrary raw SQL fragments or unvalidated user-chosen SQL identifiers safe.
$model = new \App\Models\TaskModel();

$all = $model->findAll();
$one = $model->find(3);

$pending = $model
    ->where('status', 'pending')
    ->orderBy('created_at', 'DESC')
    ->findAll();

Read the chain as: keep matching rows → choose their order → retrieve them.

  • where() restricts results; orderBy() sorts them. DESC means descending and ASC ascending.
  • For a creation date, descending usually places newer records first. Equal timestamps may need an additional ordering key if a precise tie order matters.
Method Purpose Typical result
findAll() Retrieve the model’s matching records Many rows
find($id) Retrieve one primary-key match One row or null
where('status', 'pending') Add a condition Query/model chain, not the final list
orderBy('created_at', 'DESC') Add ordering Query/model chain
like('title', 'report') Add text-search matching Query/model chain
limit(5) Limit returned rows Query/model chain
countAllResults() Count matching records A count
first() Retrieve the first matching record One row or null

The default examples work with associative arrays, hence $task['title']. A model can be configured to use other return types, but do not switch syntax halfway through the course example.

2.5 Connect the model, controller, route, and list view

PDF pages 28–31 · Complete list-page handoff ↗

// app/Config/Routes.php
$routes->get('/tasks', 'Tasks::index');

// app/Controllers/Tasks.php
<?php
namespace App\Controllers;
use App\Models\TaskModel;

class Tasks extends BaseController
{
    public function index()
    {
        $model = new TaskModel();
        $data['tasks'] = $model->findAll();
        return view('tasks/index', $data);
    }
}

<!-- app/Views/tasks/index.php -->
<h1>My Tasks</h1>
<ul>
<?php foreach ($tasks as $task): ?>
    <li><?= esc($task['title']) ?> — <?= esc($task['status']) ?></li>
<?php endforeach; ?>
</ul>

The controller creates the model, retrieves records, and passes a tasks key to the view. That key becomes $tasks. foreach visits each row, assigning it to $task. esc() escapes display values so text is not interpreted as HTML markup.

The alternative $tasks = model(TaskModel::class)->findAll(); uses CodeIgniter’s model() helper instead of explicit new TaskModel(). Both styles in the PDF reach the same kind of model operation. Use the necessary import or fully qualified class name.

2.6 One-record pages and missing records

PDF pages 32–36 · Details, null handling, and recap ↗

// Route
$routes->get('/tasks/(:num)', 'Tasks::show/$1');

// In Tasks controller
public function show($id)
{
    $model = new TaskModel();
    $task = $model->find($id);
    if ($task === null) {
        throw \CodeIgniter\Exceptions\PageNotFoundException::forPageNotFound();
    }
    return view('tasks/show', ['task' => $task]);
}

<!-- app/Views/tasks/show.php -->
<h1><?= esc($task['title']) ?></h1>
<p>Status: <?= esc($task['status']) ?></p>

The route supplies the ID; find() searches by the configured primary key. A numeric URL component does not guarantee a matching row. Check for null before trying to display a field. The fully qualified exception in this rewritten example makes the class reference explicit; it expresses the missing-record response introduced in the slides.

M2 in one chain: .env connects → model identifies the table → query retrieves records → controller passes an array → view displays escaped values.

  • If records fail to appear, check the database and query result before blaming the view.
  • Common faults are a wrong table name, missing writable-field configuration during saves, missing sample rows, and using a nonexistent record without checking it.
  • The opening objectives and final recap/Q&A frame these same database tasks.

2.7 Additional configuration and query examples

PDF pages 7–35 · Connection defaults, query methods, and output ↗

The database must exist before the task-table SQL runs. The slides use phpMyAdmin through XAMPP to create that database. The CREATE TABLE statement creates the table inside the selected database. The later INSERT statement supplies the three demonstration rows.

The PDF also shows the corresponding entries in app/Config/Database.php:

'hostname' => 'localhost',
'username' => 'root',
'password' => '',
'database' => 'your_database_name',
'DBDriver' => 'MySQLi',

These entries belong inside the existing database connection configuration. They are not a complete replacement for the configuration file. Matching .env values override these defaults. Start the application with php spark serve, then request a database-backed page to test the connection.

Read the additional Query Builder methods as operations, not only names. These examples expand the method descriptions on p. 27:

// Find titles containing the keyword.
$matches = $model->like('title', 'report')->findAll();

// Retrieve no more than five matching records.
$few = $model->where('status', 'pending')->limit(5)->findAll();

// Return a number instead of the matching rows.
$count = $model->where('status', 'pending')->countAllResults();

// Return one matching record, or null.
$first = $model->where('status', 'pending')->first();

Use a deliberate order when the identity of the first row matters. A limit controls the number of results; it does not choose a meaningful order by itself.

The model helper and direct construction are alternatives:

use App\Models\TaskModel;

$model = new TaskModel();
$tasks = $model->findAll();

// Alternative:
$tasks = model(TaskModel::class)->findAll();

For the sample records, /tasks/3 displays Fix login bug with status done.

  • This result depends on the inserted IDs. The URL number is not an array position.
  • The controller passes the singular task key to app/Views/tasks/show.php; the list uses the plural tasks key.

Escaping query values and escaping HTML output are separate operations. The query tool handles normal query values. esc() handles displayed text in the view. Neither operation replaces the application's validation rules.

Apply the concepts: distinguish the result you need

These worked situations use the module’s database and model responsibilities with new record values.

Situation 1 — Show three pending tasks, newest first.

  1. Select the model for the tasks table.
  2. Filter the status to pending.
  3. Order the creation time in descending order.
  4. Limit the result to three records.
  5. Execute retrieval and pass the resulting rows to the view.
$tasks = $model->where('status', 'pending')
    ->orderBy('created_at', 'DESC')
    ->limit(3)
    ->findAll();

Reason: filtering answers “which rows?” Ordering answers “in which order?” Limiting answers “how many at most?” Retrieval actually returns the rows.

Situation 2 — A details URL requests a missing task.

  1. Call find($id) for the selected primary key.
  2. Check whether the result is null.
  3. Return an appropriate not-found response before reading the title.

Result: do not substitute the first available row. That would display a different task from the one requested.

Situation 3 — The page works, but the database test fails.

  • Connection refused — check the service and configured address/port.
  • Unknown database — check whether the configured database exists.
  • Access denied — check the account, password, and permitted access.
  • Correct records but wrong display — inspect the view-data key, row shape, and escaped output.

Exam cue: separate connection, query, result shape, and presentation. A working welcome page does not prove that the database works.

3.1 The complete form workflow

PDF pages 1–9 · Objectives, request methods, CSRF, and submitted values ↗

Key terms — identify the job

  • GET form action — The handler that displays the form.
  • POST submission — The request that sends the fields for a server-side decision.
  • Validation — The checkpoint that tests input before the write.
  • Old input — The previously submitted values made available when the form returns after failure.
  • CRUD — Create, Read, Update, Delete: the four record operations.
  • Uploaded file — A file object read from the upload field, rather than an ordinary text value.
  • Stored filename — The generated reference saved in the database for the public-upload pattern.
  • Public URL — The address the browser uses to request the file; it differs from a server filesystem path.

A form is the interface for collecting data; it is not proof that the data is correct. A visitor can send blank values, unexpected field names, or a request constructed without your page. Validate on the server before writing the record. Browser-side checks alone are not the controller’s validation.

The course uses two routes for adding a task:

$routes->get('/tasks/new', 'Tasks::new');
$routes->post('/tasks', 'Tasks::create');

GET displays the form. POST submits data to the create action. The same path can serve different purposes under different HTTP methods. Use php spark routes to inspect registered method/path/handler combinations before debugging a form that seems to go nowhere.

<!-- app/Views/tasks/new.php -->
<form method="post" action="<?= site_url('tasks') ?>">
    <?= csrf_field() ?>
    <label for="title">Title</label>
    <input id="title" type="text" name="title"
           value="<?= old('title') ?>">
    <?= validation_show_error('title') ?>
    <button type="submit">Add Task</button>
</form>

action is the destination URL.

  • method determines the request method. name="title" determines the submitted key, so the controller, validation rule, and error lookup must use title too.
  • site_url() builds an application URL instead of assuming a fixed folder location.
  • The controller reads the value through $this->request->getPost('title') rather than relying directly on $_POST.

csrf_field() renders a hidden CSRF-token field.

4.1 Sessions give separate requests continuity

PDF pages 1–9 · Objectives, session data, and removal ↗

Key terms — identify the job

  • Session — Small server-side state associated with a visitor across separate requests.
  • Session cookie — The browser’s identifier for the associated session; it is not the user’s stored password.
  • Flash data — Session data intended for the next-request feedback cycle.
  • Password hash — The stored password representation created by password_hash().
  • Verification — The password_verify() check of a candidate against its stored hash.
  • Authentication — The identity check: who is the visitor?
  • Authorization — The access decision: may this visitor perform this operation on this record?
  • Authentication filter — A server-side gate attached to protected routes; its before() hook can stop the action.

HTTP requests are separate exchanges.

  • A session lets the server associate small pieces of state with the same visitor across requests.
  • The browser commonly sends a session cookie identifying the relevant server-side session data.
  • The cookie is not a reason to store the user’s password in session data.
session()->set('username', 'admin');
$name = session()->get('username');
$sameName = session('username');

session()->remove('username'); // One key
session()->destroy();          // End the whole session

Use the CodeIgniter session service/helper; the course does not manually call PHP’s session_start().

  • set() remembers a value, get() reads it, and remove() removes a particular key.
  • Destroying the session ends the whole login state rather than removing one value and accidentally leaving others behind.
Appropriate small values Values the module says to avoid
User ID, username, login-state flag Plaintext password or stored password hash as a login credential
A short redirect message Whole user tables or large record collections

A session remembers state, not permission by itself. Application code must check the relevant state before allowing a protected action. Session lifetime also depends on configuration and expiration; “lasts the visit” is a teaching shorthand, not a guaranteed duration for every setup.

4.2 Flash data is for the next request

PDF pages 10–15 · Redirect messages and session habits ↗

Flash data is session data intended to survive into the next request and then expire. It fits the save–redirect–display pattern because the message is set before the redirect and shown on the destination page.

// After a successful task insert:
session()->setFlashdata('message', 'Task added successfully!');
return redirect()->to('/tasks');

<!-- In the destination view -->
<?php if ($message = session()->getFlashdata('message')): ?>
    <p class="success"><?= esc($message) ?></p>
<?php endif; ?>

The key message must match on both sides. Set the message before returning the redirect; code after a return is not reached. The esc() call makes output handling explicit in this rewritten view.

Not “deleted because it was read”

The next-request lifecycle is the important rule. Reading flash data is not the same as immediately deleting it on that read. The CodeIgniter session documentation describes its request-based availability.

Example: POST creates a task and sets message; GET /tasks after the redirect displays it.

  • A later ordinary refresh should not keep reporting that a new task was just created.
  • A persistent set() value would be the wrong tool for a message meant to disappear.

4.3 Password storage and authentication

PDF pages 16–20 · User records, hashing, and demo setup ↗

Authentication checks who the visitor is.

  • The course’s minimal login looks up a user by username and verifies the typed password against a stored password hash.
  • A users table therefore needs an ID, a unique username, and a password-hash column, illustrated as VARCHAR(255).
$hash = password_hash($plainPassword, PASSWORD_DEFAULT);
// Persist $hash in users.password, never $plainPassword.

password_hash() creates a password hash suitable for storage. PASSWORD_DEFAULT selects PHP’s default password-hashing algorithm. It is not encryption that the application later decrypts. Verification checks a candidate password against that hash.

// app/Models/UserModel.php
<?php
namespace App\Models;
use CodeIgniter\Model;

class UserModel extends Model
{
    protected $table = 'users';
    protected $allowedFields = ['username', 'password'];
}

The slides create one hashed test account so the login query has a real row to find.

  • The displayed demo credentials are classroom examples, not values to reuse in a real deployment.
  • A model definition alone does not create the table or the account.
Hash and verify are a pair

Store with password_hash(); check with password_verify(). Do not compare the typed password directly with the stored hash using == or ===, and do not re-hash the typed value and compare hash strings.

4.4 Trace the login controller from input to session

PDF pages 21–25 and 32 · Form, lookup, verification, and success ↗

The login form submits username and password to the login POST route, includes csrf_field(), and uses a password input to obscure the on-screen characters. An HTML password field does not hash the stored password or replace secure transport.

The controller needs to read both submitted variables before using the verification fragment. This combined teaching example supplies the password assignment that is implicit in the slides:

// In the Auth controller; import App\Models\UserModel.
$username = $this->request->getPost('username');
$password = $this->request->getPost('password');

// Validate required field types/presence before this lookup.
$model = new UserModel();
$user = $model->where('username', $username)->first();

if (! $user || ! password_verify($password, $user['password'])) {
    session()->setFlashdata('error', 'Invalid login.');
    return redirect()->back()->withInput();
}

// Explicit safety addition after establishing a new login:
session()->regenerate(true);
session()->set([
    'isLoggedIn' => true,
    'user_id' => $user['id'],
    'username' => $user['username'],
]);
return redirect()->to('/tasks');

The first condition rejects an absent user before attempting to read their stored hash.

  • The failure message is generic. The success branch remembers only the small values needed for subsequent requests.
  • The session-ID regeneration line is labeled as an addition; it is not printed in the PDF’s short successful-login snippet.

Read this in order: validate input → find username → verify password → establish session state → redirect. The protected task page is reached by a new request, which is why the login state must persist in the session.

4.5 Filters centralize protected-route checks

PDF pages 27–31 · before(), after(), alias, and route attachment ↗

A filter can run before controller logic.

  • The authentication filter checks whether the login flag exists and is true.
  • If the visitor is a guest, it returns a redirect to /login before allowing the task action to run.
  • Repeating this check manually in every action is harder to maintain and easier to forget.
// app/Filters/AuthFilter.php
<?php
namespace App\Filters;

use CodeIgniter\Filters\FilterInterface;
use CodeIgniter\HTTP\RequestInterface;
use CodeIgniter\HTTP\ResponseInterface;

class AuthFilter implements FilterInterface
{
    public function before(RequestInterface $request, $arguments = null)
    {
        if (! session()->get('isLoggedIn')) {
            return redirect()->to('/login');
        }
    }

    public function after(RequestInterface $request,
        ResponseInterface $response, $arguments = null) {}
}

before() is the pre-controller gate. after() is the corresponding post-controller hook; this simple filter does not need to change the response there. Register the alias in app/Config/Filters.php by adding it to the existing aliases, rather than accidentally replacing other framework aliases:

'auth' => \App\Filters\AuthFilter::class,

Then attach it to a protected route:

$routes->get('/tasks', 'Tasks::index', ['filter' => 'auth']);
Protect actions, not just page links

Every route requiring login needs the check, including write routes. Hiding an Edit or Delete control does not prevent a direct HTTP request. Authentication answers “logged in?”; role and record-ownership permissions need additional checks.

6.2 Migrations describe schema changes

A migration versions a database structure change as code. Laravel records which migrations have run. This helps different project copies create the same tables instead of manually clicking an undocumented schema into existence.

php artisan make:migration create_tasks_table

The first command is the explicit generation command for the migration step described in the PDF; define the schema before running migrate.

// Inside the migration's up() method:
Schema::create('tasks', function (Blueprint $table) {
    $table->id();
    $table->string('title', 150);
    $table->string('status', 20)->default('pending');
    $table->timestamps();
});

id() creates the conventional ID column.

  • string('title', 150) gives the column its length. default('pending') supplies a default status. timestamps() adds both created_at and updated_at, matching Eloquent’s usual timestamp behavior.
  • Other illustrated column choices include nullable text for notes and a boolean is_active with a false default.
Command Effect to recognize
php artisan migrate Run pending migrations
php artisan migrate:rollback Roll back the latest migration batch
php artisan migrate:fresh Drop tables and rebuild using migrations
These commands are not synonyms

6.4 Eloquent models and mass assignment

Eloquent is Laravel’s object-relational mapper. A model class represents the application’s interaction with a table; a model instance represents one record. A set of results is commonly returned as a collection of model instances.

php artisan make:model Task

use Illuminate\Database\Eloquent\Model;

Key terms — identify the job

  • edit / update — Display the selected record’s form / receive its intended changes.
  • Named route — A label used by route() to generate a URL; it is not a template filename.

7.6 Replacement order and image preparation

The module’s checklist says to delete old files only after replacement succeeds.

  • Its short p. 28 fragment deletes the old file before storing the new one.
  • Those are not equivalent in a failure case: if storage fails after deletion, the old attachment is gone and no working replacement exists.
Use the complete checklist to resolve the short snippet

For a replacement, validate first, store/process the new file, save its new path successfully, then remove the old file. If saving the new path fails, clean up the newly stored file and retain the old reference. File storage and a database update are separate operations; a database transaction alone does not undo filesystem changes.

Conceptually, the sequence is:

Remember old path
    → validate and store the replacement
    → successfully update the task's path
    → delete the old path from the same disk

            ->store('attachments', 'public');
        $task->update(['attachment' => $path]);
    }

    return redirect()->route('tasks.show', $task);
}

This example assumes the required imports, database column, fillable field, and successful file/database operations. It illustrates a new upload, not the full failure-handling sequence for replacing an old file.

The optional image-processing example creates a filename with uniqid('avatar_') . '.jpg'.

  • Its absolute write destination is storage_path('app/public/attachments/' . $name). Save the corresponding relative value attachments/ plus that filename in the database.
  • Do not save both the raw uploaded file object and a generated path as competing representations of the same attachment.

Image::read(...)->cover(300, 300)->save($path) processes and saves the image. store('attachments', 'public') stores an uploaded file. These are different example paths through the file workflow. Select the intended path and preserve validation, directory setup, path persistence, and cleanup around it.

Apply the concepts: preserve the record and its attachment

These situations apply the module’s form, binding, validation, and storage sequence.

Situation 1 — The edit form cannot reach its PATCH action.

  1. Check the form’s target named route and selected task parameter.
  2. Use a normal POST form.
  3. Include @csrf for the protected web submission.
  4. Include @method('PATCH') to express the intended update method.

Reason: the hidden method field and token have different jobs. Neither selects an incorrectly named route for the form.

Situation 2 — Replacing an image removes the old image, then fails.

  1. Establish the selected record and access.
  2. Validate the new upload before replacing anything.
  3. Store the new file and check the operation’s result.
  4. Persist the new relative path through a checked record update.
  5. Remove the previous file only when the replacement is established.
  6. Handle failures and remove an unused new file when necessary.

Reason: filesystem changes and database changes are separate operations. They do not automatically undo each other. If no replacement is supplied, keep the existing attachment unless removal is explicitly intended.

Situation 3 — The stored file exists, but the public image is broken.

  • Stored value: attachments/generated.png is a relative disk path.
  • Public URL: prefix it with the intended storage/ URL segment once.
  • Local setup: confirm the public/storage link for the public disk.
  • Cleanup: use the same disk and relative path when deleting the file.

Exam cue: binding finds the record; authorization permits the operation; validation checks the fields; storage handles the file. Passing one does not replace the others.

8.1 A resource controller gives CRUD a standard map

Key terms — identify the job

  • Resource controller — A controller with the standard CRUD action names.
  • Resource route — The conventional URL-and-method map to those actions.
  • Auth middleware — The route gate that requires authentication.
  • Owned-record query — A query restricted through the current user’s relationship or equivalent access condition.
  • Mailable — The class that receives data and describes an email’s content.
  • Transport — The configured mail connection used to send the message.
  • Recipient — The address passed to Mail::to(); it differs from the configured sender.
  • Transition — A saved change from one state to another, such as pending → done.

Full CRUD is the complete create/read/update/delete workflow for a resource. Laravel’s resource controller uses conventional action names so another developer can predict which method shows a form and which method saves it.

php artisan make:controller TaskController --resource --model=Task
php artisan route:list --name=tasks

The generator creates a controller skeleton. The option is typed with two ordinary hyphens: --resource; the slide’s typographic dash should not be pasted as a different terminal character. Register the route before expecting it to appear in route:list:

use App\Http\Controllers\TaskController;
Route::resource('tasks', TaskController::class);
HTTP method URL Controller action Route name Purpose
GET /tasks index tasks.index List records
GET /tasks/create create tasks.create Show the new-record form
POST /tasks store tasks.store Validate and save a new record
GET /tasks/{task} show tasks.show Show one record
GET /tasks/{task}/edit edit tasks.edit Show an existing-record form
PUT/PATCH /tasks/{task} update tasks.update Validate and save changes

Four CRUD operations, seven standard actions

8.4 Owning records is separate from being logged in

Associate each task with its owner. The course adds a user_id foreign key and a relationship on User:

// In the task-table schema / appropriate migration:
$table->foreignId('user_id')->constrained();

// In User.php; import App\Models\Task:
public function tasks()

    return $this->hasMany(Task::class);

// After validating title:
$request->user()->tasks()->create($validated);

// Current user's list:
$tasks = $request->user()
    ->tasks()
    ->latest()

Creating through the authenticated user’s tasks() relationship associates the task with that user.

  • Reading through the relationship scopes the list by user_id. Do not trust a posted user_id to decide ownership when the authenticated session already identifies the user.

Important completion of the private-record example

8.6 Send after success, and trigger on the transition

PDF pages 30–35 · Sending, completed workflow, notification design, and recap ↗

use App\Mail\TaskCompletedMail;
use Illuminate\Support\Facades\Mail;

// $validated comes from the intended update rules.
// The task has already passed its access check.
$task->update($validated);

if ($task->wasChanged('status') && $task->status === 'done') {
    Mail::to($request->user()->email)
        ->send(new TaskCompletedMail($task));
}
return back()->with('status', 'Status updated');

This combines the update/send example with the safer trigger shown on p. 33. Mail::to(...) selects the recipient; send(...) dispatches the constructed mailable. The with('status', ...) value is a short redirect message for the next page, not the database task status field.

$task->status === 'done' alone asks whether the task is currently complete.

  • It would also be true on a later title-only edit. wasChanged('status') asks whether that attribute changed in the just-saved model operation.
  • Together, the checks target a change to done, avoiding routine resends when an already-complete task is edited without another status transition.
Make the status update possible

If this action changes status, its validated data, model fillable configuration, form, and schema must support status. A title-only validation example does not make a status transition happen. A rule such as in:pending,done is an illustrative application rule for the two states used by the course.

The sample assumes a successful model save.

  • A full application also handles save/mail failures. The condition is not an exactly-once delivery guarantee under retries or concurrent requests, and a later genuine transition back to done can legitimately trigger another email.
  • The course’s practical lesson is to send after the successful change, keep sensitive data out of mail, and test with safe settings.

Apply the concepts: connect CRUD, access, and notification

These situations combine the responsibilities already taught across the Laravel modules.

Situation 1 — The user’s list is private, but a guessed task URL exposes another record.

  1. Confirm that authentication protects the request.
  2. Check how the selected task is resolved.
  3. Apply the intended ownership restriction to that record action.
  4. Repeat the check for show, edit, update, destroy, and upload.

Reason: a scoped index limits one query. It does not automatically authorize later requests to individual IDs.

Situation 2 — A completed task sends another completion email after a title edit.

State before save State after save Status changed? Completion trigger?
pending done Yes Yes, after the save succeeds
done done No No
done pending Yes No
pending pending No No
  1. Save the validated, authorized change successfully.
  2. Check whether status changed in that save.
  3. Check whether the resulting status is done.
  4. Send only when both trigger conditions are true.

  • Content: the mailable and Markdown view build the message.
  • Recipient: Mail::to(...) selects the intended destination.
  • Transport: valid test-service settings establish the outgoing connection.
  • Trigger: the controller decides when the saved business change warrants sending.
