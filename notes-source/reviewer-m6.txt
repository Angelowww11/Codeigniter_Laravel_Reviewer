### 6.1 Six pieces of the Laravel data layer
<p class="page-range">PDF pages 1–8 · Objectives, database choice, and file responsibilities</p>

#### Key terms and meanings

- **Migration** — A versioned schema change with forward and reverse operations.
- **Seeder** — A class that inserts intended sample records when run.
- **Eloquent model** — The class-based interface to records in a database table.
- **Query builder** — A prepared query description before a terminal operation executes it.
- **Collection** — A group of retrieved models, normally processed with a loop.
- **Mass assignment** — Writing an array of attributes through operations such as create().
- **Fillable fields** — The model’s permitted attributes for the taught mass-assignment pattern.
- **Not-found handling** — The failure path when a selected row is absent, such as findOrFail().

Laravel separates connection settings, table structure, sample rows, record access, request handling, and display. Keeping those jobs distinct makes database problems much easier to locate.

| Job | Where the course puts it | What it does not do |
| --- | --- | --- |
| Connection settings | `.env` | Does not create task columns |
| Schema | `database/migrations` | Does not automatically add demonstration tasks |
| Sample records | `database/seeders` | Does not replace the table schema |
| Record access | `app/Models/Task.php` | Does not decide page layout |
| Request coordination | `app/Http/Controllers` | Does not belong inside Blade |
| Presentation | `resources/views` | Should not fetch its own database records |

The module starts with SQLite, which stores the local database in one file, and notes that MySQL can be used by changing connection settings.

- For SQLite, the driver is `DB_CONNECTION=sqlite`; where an explicit database path is configured, it must point to the actual file.
- MySQL instead needs the corresponding host, database name, and credentials.

The printed `type nul > database\database.sqlite` is a **Windows Command Prompt** file-creation example, not a Laravel API or a command that works identically in every shell.

- The conceptual steps are to ensure the configured SQLite file exists and then run migrations.
- Do not accidentally truncate an existing database while following a setup example.

### 6.2 Migrations describe schema changes
<p class="page-range">PDF pages 9–12 · Columns, migration execution, and rollback</p>

A **migration** versions a database structure change as code. Laravel records which migrations have run. This helps different project copies create the same tables instead of manually clicking an undocumented schema into existence.

```sh
php artisan make:migration create_tasks_table
php artisan migrate
```

The first command is the explicit generation command for the migration step described in the PDF; define the schema before running `migrate`.

```php
// Inside the migration's up() method:
Schema::create('tasks', function (Blueprint $table) {
    $table->id();
    $table->string('title', 150);
    $table->string('status', 20)->default('pending');
    $table->timestamps();
});
```

`id()` creates the conventional ID column.

- `string('title', 150)` gives the column its length. `default('pending')` supplies a default status. `timestamps()` adds **both `created_at` and `updated_at`**, matching Eloquent’s usual timestamp behavior.
- Other illustrated column choices include nullable text for notes and a boolean `is_active` with a false default.

| Command | Effect to recognize |
| --- | --- |
| `php artisan migrate` | Run pending migrations |
| `php artisan migrate:rollback` | Roll back the latest migration batch |
| `php artisan migrate:fresh` | Drop tables and rebuild using migrations |

<aside class="notes-important"><strong>These commands are not synonyms</strong><p><mark><code>migrate:fresh</code> destroys existing tables/data.</mark> The module reserves destructive reset commands for disposable local development. A rollback also depends on the migration’s reverse operation; it is not simply “undo my last typed SQL.”</p></aside>

### 6.3 Seeders create repeatable sample records
<p class="page-range">PDF pages 13–15 · Seeder generation and inserts</p>

A **seeder** inserts predictable data. A migration makes a table available; a seeder gives the list view records to display.

```sh
php artisan make:seeder TaskSeeder
php artisan db:seed --class=TaskSeeder
```

```php
// In TaskSeeder::run(); import App\Models\Task.
Task::create(['title' => 'Buy groceries', 'status' => 'pending']);
Task::create(['title' => 'Submit report', 'status' => 'pending']);
Task::create(['title' => 'Fix login bug', 'status' => 'done']);
```

This completes the three sample rows used by the later list screens; the PDF’s p. 14 code is visually cut off near the third insertion.

- The `Task` model, table, and allowed mass-assignment fields must exist before this example runs.
- Re-running a simple insert-only seeder can create duplicates; a seeder is not automatically a synchronization script.

### 6.4 Eloquent models and mass assignment
<p class="page-range">PDF pages 16–20 · ORM, Task model, and fillable fields</p>

**Eloquent** is Laravel’s object-relational mapper. A model class represents the application’s interaction with a table; a model instance represents one record. A set of results is commonly returned as a collection of model instances.

```sh
php artisan make:model Task
```

```php
// app/Models/Task.php
<?php
namespace App\Models;
use Illuminate\Database\Eloquent\Model;

class Task extends Model
{
    protected $fillable = ['title', 'status'];
}
```

Under the convention used here, `Task` maps to `tasks`, its primary key is `id`, and timestamps use the conventional columns. These conventions explain why the Laravel example needs fewer explicit table properties than `TaskModel` in CodeIgniter.

`$fillable` identifies attributes allowed through mass-assignment operations such as `create([...])` and `update([...])`. It is comparable in purpose to CodeIgniter’s `$allowedFields` for the course’s writes. <mark>It does not validate input or authorize the person performing the write.</mark> A column must still exist in the schema, and validation should still return the fields you intend to save.

### 6.5 Reading many records and explaining the result
<p class="page-range">PDF pages 21–24 and 26–28 · Collections, queries, view data, and routes</p>

```php
use App\Models\Task;

$tasks = Task::all();
return view('tasks.index', compact('tasks'));
```

`Task::all()` retrieves all tasks. `compact('tasks')` is a PHP helper that builds `['tasks' => $tasks]` from an existing local variable; it does not query the database. `view('tasks.index')` uses Laravel’s dotted view naming and resolves to `resources/views/tasks/index.blade.php`.

For a filtered, ordered list:

```php
$tasks = Task::where('status', 'pending')
    ->orderBy('created_at', 'desc')
    ->get();
```

Read the chain as **condition → order → execute retrieval**. `get()` retrieves the query’s results. `all()` is the simple retrieve-everything method, not the terminal method to append after a `where()` chain in these examples.

```html
<!-- resources/views/tasks/index.blade.php -->
<h1>My Tasks</h1>
<ul>
@foreach ($tasks as $task)
    <li>
        {{ $task->title }}
        @if ($task->status === 'done')
            <span>Done</span>
        @else
            <span>Pending</span>
        @endif
    </li>
@endforeach
</ul>
```

`$tasks` is the collection; `$task` is one model object, so attributes use `->title` and `->status`.

- Contrast that with the CodeIgniter array example’s `$task['title']`. Blade’s loop and condition control presentation; they do not move database queries into the template.
- `{{ }}` escapes the displayed values.

Register GET `/tasks` to `TaskController::index` and GET `/tasks/{id}` to `TaskController::show`, importing the controller in `routes/web.php` as in M5. The route connects the request to the data-loading action; it does not replace that action.

### 6.6 One record, 404s, and debugging the data
<p class="page-range">PDF pages 25 and 29–34 · Details, assembled flow, Tinker, and recap</p>

```php
public function show($id)
{
    $task = Task::findOrFail($id);
    return view('tasks.show', compact('task'));
}
```

```html
<!-- resources/views/tasks/show.blade.php -->
<h1>{{ $task->title }}</h1>
<p>Status: {{ $task->status }}</p>
```

`findOrFail()` retrieves one primary-key match or raises the missing-model exception that Laravel normally turns into a 404 response.

- That is different from CodeIgniter’s earlier `find()` example, where the controller explicitly checks for null.
- Do not blindly access a field on a missing record.

**Tinker** is an interactive Laravel/PHP shell useful for checking whether data exists before debugging the page:

```text
php artisan tinker
>>> App\Models\Task::count();
3
>>> App\Models\Task::first()->title;
"Buy groceries"
```

The printed results assume the three seeded rows exist. `first()->title` also assumes `first()` found a model; an empty table requires a null check. Tinker is a development inspection tool, not part of the Blade page shown to visitors.

**M6 recap:** configuration connects, migration creates schema, seeder inserts sample records, Eloquent queries models, controller supplies data, and Blade displays it.

- If the page is empty or fails, inspect connection/path, migration state, seed rows, model import, `$fillable` for writes, and the data passed to the view.
- The opening objectives and final recap/Q&A align with these responsibilities.


### 6.7 Additional migration, seeder, and route connections
<p class="page-range">PDF pages 7–33 · Executable context for the data examples</p>

The schema example belongs inside the generated migration's `up()` method. The generated file imports `Schema` and `Blueprint`. A typical reverse operation removes the table:

```php
public function down(): void
{
    Schema::dropIfExists('tasks');
}
```

This is explanatory migration context. A rollback calls reverse operations for the selected migration batch. It does not recover records that a destructive schema operation removed.

The column examples on p. 11 are alternatives selected for application requirements:

```php
$table->string('title', 100);
$table->text('notes')->nullable();
$table->boolean('is_active')->default(false);
```

`nullable()` permits SQL NULL for that column. `default(false)` supplies a value when an insertion omits `is_active`. The earlier task schema uses a 150-character title; this slide illustrates column choices rather than a second simultaneous definition of the same column.

Place `TaskSeeder` in `database/seeders/TaskSeeder.php`. Import `App\Models\Task` before calling `Task::create()`. Put the insert calls inside `run(): void`. Run `php artisan db:seed --class=TaskSeeder` after the table and model exist.

The list and details routes need the controller import:

```php
use Illuminate\Support\Facades\Route;
use App\Http\Controllers\TaskController;

Route::get('/tasks', [TaskController::class, 'index']);
Route::get('/tasks/{id}', [TaskController::class, 'show']);
```

The details action receives an ID in this module. M7 later demonstrates a bound `Task $task` parameter. Do not combine the two signatures without matching the route and lookup code.

The list view uses `resources/views/tasks/index.blade.php`. The details view uses `resources/views/tasks/show.blade.php`. `view('tasks.index', compact('tasks'))` and `view('tasks.index', ['tasks' => $tasks])` provide the same named view variable.

For the three seeded rows, the list shows two pending tasks and one completed task.

- The Blade condition converts stored `done` into the display label `Done`. The other branch prints `Pending`.
- This example assumes the course's two status values; it does not validate arbitrary stored statuses.

<mark>A working migration, model, and route do not prove that seed records exist.</mark> Check `Task::count()` in Tinker before changing a correctly written empty-list view.

#### Workflow notes: schema, sample records, and model results

Database setup and retrieval produce different results at different stages.

##### Schema and seed records in a new local database

1. Confirm the active database connection or SQLite file.
2. Confirm that the relevant migration ran there.
3. Check the actual row count with a suitable development query.
4. Run the intended seeder if the sample records have not been inserted.
5. Check the controller’s view-data key and Blade loop if rows exist.

**Reason:** a migration creates schema; it does not imply that a seeder ran. An empty collection can be the correct query result.

##### Collections, single models, and counts

- `get()` / `all()` — multiple-model collection; normally loop over its models.
- `first()` — one matching model or no result; check the missing-result path.
- `findOrFail($id)` — one primary-key model or the not-found path.
- `count()` — a number; it does not supply titles or model properties.

**Reason:** choose the result contract before choosing the API. Reading `->title` from an entire collection confuses two different shapes.

##### Schema, writable fields, and validation

1. Check the column’s storage definition.
2. Check whether the model permits that intended mass-assigned field.
3. Check the request’s acceptable-value rules.

**Reason:** schema, `$fillable`, and validation are separate controls. A permitted writable string is not automatically a meaningful valid title.

**Key connection:** avoid destructive reset commands as a default repair. Rollback and recreation do not guarantee recovery of records that were removed.
